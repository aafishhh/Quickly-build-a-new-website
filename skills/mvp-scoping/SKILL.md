# 构造 MVP：产品落地设计蓝图

## Overview

立项 skill（new-website-ideation）回答了「**为什么做**」——用户、痛点、凭什么赢、最小做哪几个功能（08-prd.md）。本 skill 回答「**做成什么样**」——把 MVP 范围翻译成可以动手的落地设计：
- **页面地图**（信息架构）：整个 MVP 拆成哪几个页面，页面间怎么导航
- **每页结构 + 功能**：每页分哪几个区块、各区块放什么、核心交互和功能清单
- **核心用户流**：用户从进来 → 完成核心动作 → 得到结果，每一步落在哪个页面/区块
- **视觉与样式规范**：配色/圆角/字体基调，关键组件样式（按钮/输入框/卡片/加载/错误态）
- **数据与状态**：要存什么、每页的空态/加载/成功/失败

这套设计蓝图交给后续 skill（建站落地 tool-site-foundation / 开发），让「做哪些页、每页长什么样、用户怎么走」一次想清楚，不边写边纠结界面。

三 skill 分工（边界清晰、不重复）：
| Skill | 回答的问题 | 产出 |
|---|---|---|
| `new-website-ideation` | 为什么做（用户/痛点/凭啥赢/最小做啥） | `08-prd.md` 业务结论 |
| `mvp-scoping`（本） | 做成什么样（页面地图/每页功能/样式/主流程） | 产品落地设计蓝图 |
| `tool-site-foundation` | 用什么技术做（技术栈/部署/通用模块） | 基建方案 |

## Workflow Decision Tree

- 已读完 `08-prd.md`、要设计 MVP 页面结构 → 从 Step 1 走全流程
- 只有想法、没走立项 → 先建议跑一遍 `new-website-ideation` 有 `08-prd.md` 再进本 skill（本 skill 依赖其 MVP 范围）
- 页面地图已清楚，只差某几页的细节/样式 → 直接跳到对应 Step
- 已有一个参考站/竞品界面 → Step 1 直接带入其页面结构做差异化

## 输出目录约定

承接立项：若同一项目已用 `new-website-ideation`，沿用同一目录 `product/<项目slug>/`，追加命名空间避免覆盖立项的 01-08：

| 文件 | 内容 |
|---|---|
| `10-wireframe.md` | 页面地图（信息架构）+ 页面间导航 |
| `11-pages.md` | 每页结构 + 区块 + 功能清单 |
| `12-main-flow.md` | 核心用户流（逐步走通主流程） |
| `13-visual-spec.md` | 视觉与样式规范 |
| `14-data-state.md` | 数据 + 每页状态（空/加载/成功/失败） |
| `15-scoping-summary.md` | 汇总蓝图（最终交给建站/开发） |

若项目没走立项、独立使用，可放 `design/<项目slug>/` 下。

## Step 1: 输入确认 + 页面地图（10-wireframe.md）

先读 `08-prd.md` 锁定 MVP 范围与「不做」清单（本 step 的边界来源），然后：
- **拆页面**：整个 MVP 需要哪几个页面/视图（如：首页、工具页、登录、定价、我的/账户、后台）。工具站常见：首页(Hero+工具入口) / 工具落地页 / 定价 / 登录 / 我的(任务历史/额度) / 后台
- **页面间关系**：哪些页面可达哪些页面（导航/CTA/登录墙），画一个页面地图（可文本层次或 mermaid 图）
- **砍页**：对照「不做」清单，把不必需的页面直接砍掉，只保留核心路径

每页一句话说明用途，标 `[assumption]` 指出未经用户确认的页面必要性。

## Step 2: 每页结构 + 功能（11-pages.md）

对每个保留页面，逐页写：
- **区块布局**（从上到下，如首页：Hero 输入条 → 功能示例 → 特性/场景 → 三步骤 → 对比表 → FAQ → 尾页 CTA）
- **核心交互**：该页最关键的操作（输入/上传/点击/提交），每一步的状态反馈
- **功能清单**：该页承载的所有功能，打标（P0 必须 / P1 加分）
- **与立项范围对齐**：确认该页功能没超出 `08-prd.md` 的 MVP 边界

⚠️ 对齐用户惯例：工具类落地页往往复用首页的输入组件/预设示例，避免自造新组件；同一功能只做一个入口，不重复。

## Step 3: 核心用户流（12-main-flow.md）

走一遍**主流程**（本 MVP 成立的唯一动作），逐步标注：
- 起点（从哪进来：首页 / 外部链接 / 广告）→ 每一步落在哪页哪个区块
- 核心动作（输入/上传/配置 → 触发）→ 中间态（加载/排队/预览）
- 结果产出（得到什么：一张图/一段文字/一次变更）→ 结果后动作（下载/保存/再试）
- 端到端确认：用户能否**不跳页**完成「进来→做→得→走」，漏掉的环节补上

## Step 4: 视觉与样式规范（13-visual-spec.md）

- **视觉基调**：配色（主/次/强调色）、圆角风格（圆润卡片 vs 直角）、字体基调、整体气质（可爱/专业/极客）
- **关键组件样式**（每类给一个基线）：
  - 按钮（主按钮/次按钮/危险，尺寸/圆角/悬停）
  - 输入框 / 上传区（占位、边距、错误态描边）
  - 卡片（圆角/内边距/阴影）
  - 加载态 / 错误态 / 空态（分别长什么样、文案怎么写）
- **一致性**：同类元素全站统一（同类按钮同色同圆角），不每种花样

若用户已有参考站/风格要求（如首页已有组件风格），**优先复用**，不另立新风格。

## Step 5: 数据 + 状态（14-data-state.md）

- **要存什么**：用户（登录/额度）、任务（输入/状态/结果）、结果产物（存储位置）。对照 `08-prd.md` 确认每项是 MVP 必须还是可延后
- **每页状态**：对核心页面逐个列——空态（无数据时显示什么+文案）、加载态、成功态、失败态（报错文案 + 重试）
- **边界**：登录墙放哪（要登录才能用，还是先试后登录）；未登录用户能走到哪

## Step 6: 汇总蓝图（15-scoping-summary.md）

把 1-5 的结论组装成一份给建站/开发的蓝图：
- 页面地图（哪几页、导航关系）
- 每页结构摘要 + 功能清单（含 P0/P1）
- 核心用户流（端到端路线）
- 视觉基调 + 关键组件基线
- 数据项 + 各页状态清单
- 所有 `[assumption]`（待确认项）

产出后应能直接问「谁做这些页面」——交由 `tool-site-foundation`（技术映射/基建）或开发。

## 恢复机制

- 每完成一步更新 `00-status.md`（承接立项的 00），标到哪、下一步
- 用户中断/换窗口后先读 `00-status.md` 接续，不依赖聊天记忆
- 用户已有竞品/参考界面？直接带入 Step 1 做差异化，跳过空想

## 注意事项

- **用户是决策者**：每步 AI 起草页面/样式，用户批准后才算完成；用户说改就改
- **不重复立项**：页面功能不得超出 `08-prd.md` 的 MVP 范围；「不做」清单是硬边界，发现新需求先记入 P1/后延，不擅自扩范围
- **诚实标注**：竞品界面/用户偏好不确定 → `[assumption]`，等用户确认
- **样式可具体**：用户常要的是「能直接用」的样式规范，别只给「可爱/专业」这种基调词，要落到按钮/输入框/卡片的尺寸圆角配色
- **产出不是代码**：本 skill 出设计蓝图，不写实现；技术选型交给 `tool-site-foundation`
- **合规红线**：涉及伪造凭证/证件/财务类（立项已拦）的页面一律不设计
- 与 `git-worktree-isolation` 配合：每个项目独立 worktree/分支，设计文档随项目走
