# 新网站/新产品立项（Idea → 立项文档）

## Overview

把一句模糊想法（甚至只是一句话）变成一份**可立项的业务决策文档**。核心不是写代码，是把业务想清楚：做给谁、解决什么、用户现在怎么凑合、我们凭什么赢、最小做成什么样、怎么知道成了。

本流程借鉴 `offerrev81pt/ai-pm-skills` 的 `idea-to-mvp` 方法论，按用户习惯做了中文化和业务视角改造：
- **8 步交互流程**，每步一页文档，全部落在 `product/<项目slug>/` 目录
- **用户永远是决策者**：AI 只负责起草和提问，每步由用户批准后才写入
- **诚实标注**：查不到的数据标 `[assumption]`，不把猜测包装成事实
- **可恢复、可审计**：`00-status.md` 做索引，任何时刻可从中断处接续，不依赖聊天记忆

## Workflow Decision Tree

- 有一个模糊想法，想立新项目 → 从 Step 1 开始走全流程
- 已有部分调研（竞品/用户访谈），不想重新想 → 直接写入对应步骤的 md，从 `00-status.md` 接续
- 只想快速判断「这想法值不值得做」→ 至少走完 Step 1-4（需求 + 用户 + 痛点 + 能否赢过现状），即可做 go/no-go 初判；仍有戏再补 Step 5-6
- 想法已基本清楚，只差 MVP 范围 → 从 Step 6 开始

## 输出目录约定

全部文档放在当前工作区的 `product/<项目slug>/` 下：

| 文件 | 内容 |
|---|---|
| `00-status.md` | 索引 + 当前进度（每完成一步更新） |
| `01-intake.md` | 想法到底是什么、为什么是现在 |
| `02-users.md` | 谁用、谁付费 |
| `03-use-cases.md` | 他们要完成什么、哪里痛 |
| `04-alternatives.md` | 今天怎么解决的、失败在哪 |
| `05-solutions.md` | 赢的三种方式、选哪种 |
| `06-mvp-scope.md` | 完成#1 用例的最小产品 |
| `07-validation.md` | 怎么知道有效、什么会杀死它 |
| `08-prd.md` | 组装成的精益 PRD（最终交付物） |

`<项目slug>` 用简短英文 kebab-case（如 `neighbor-tool-sharing`）。若用户在已有仓库里立新模块，也可约定放在 `docs/` 或项目文档目录。

## Step 1: 想法到底是什么（01-intake.md）

提问（一次只问 1-2 个，答完再问下一个）：
- 这个想法是什么？用一句话说清你打算做什么
- 是什么触发的——你亲身经历、观察到、还是听说的一个时刻？
- 为什么是**现在**？有什么变化让这件事变得可行/紧迫（新技术、新平台、新法规、市场变化）？

AI 职责：把用户的回答整理成 `01-intake.md`（想法一句话、触发时刻、why-now、初始范围），**列出 AI 自己的理解**让用户确认。标注哪些是用户原话、哪些是 AI 推断（标 `[assumption]`）。

## Step 2: 谁用、谁付费（02-users.md）

- 谁会用它？他们是什么身份（个人/小团队/企业）？
- **谁付费？** 用的人 = 付费的人吗？（C 端免费工具 vs B 端 SaaS 是完全不同的生意）
- 这个人群现在用什么东西解决同类问题？
- 用户规模怎么估？第一拨真实用户从哪来？

⚠️ 本步必须区分「使用者」和「付费者」，这是立项最常见的模糊点。

## Step 3: 他们要完成什么、哪里痛（03-use-cases.md）

- 用户是想用这个产品**搞定什么具体的事**（JTBD，即「用户 hire 这个产品来干的那件活」）？别停在「想要个工具」，要问到「用它把哪件麻烦事做完」
- 现在怎么做这件事？哪个环节最痛/最慢/最贵？
- 这个痛是被用户亲口说的，还是我们猜的？——被用户说过的标「访谈/评论证据」，其余标 `[assumption]`

## Step 4: 今天怎么解决的、失败在哪（04-alternatives.md）

- 现在市面上的替代方案是什么（竞品、免费工具、Excel、外包、人工）？
- 每个替代方案在哪里失败/不满足？
- 用户为什么不满意？有真实反馈证据吗（差评、论坛、评论区）？

AI 职责：能用网络搜索就搜索真实竞品，搜不到就**明确标注 `[assumption]` 并列出竞品猜测**，绝不假装调研过。

## Step 5: 赢的三种方式、选哪种（05-solutions.md）

- 发散：列出 3 种完全不同的赢法（不是 3 个功能，是 3 种定位/切入点）
- 聚合：各自的风险、成本、差异化，用户选一种
- 落盘：选定方向的「一句话定位」（给谁、解决什么、凭什么赢）

发散用「我们如何……」句式重新组织痛点；聚合时把赢不了/钱坑的方案果断划掉。

## Step 6: 完成 #1 用例的最小产品（06-mvp-scope.md）

- 哪个用例是**第一个必须成立**的？（不是最炫的，是最核心的）
- 只做这一个用例，最小功能集是什么？
- **明确写出「不做」清单**（out of scope）——立项阶段就砍掉，防止范围蔓延
- 预估：技术上有无现成方案（API/模板/开源）？最快多久能立起来？

## Step 7: 怎么知道有效、什么会杀死它（07-validation.md）

- 成功指标：用户做到什么程度算「有用」？（如：一周内 30% 用户完成核心动作）
- **什么会杀死它**：最大的 3 个致命假设是什么？哪个先验证？
- go/no-go 阈值：做到什么数字继续投入，做不到就砍/转向？

## Step 8: 组装精益 PRD（08-prd.md）

把 01-07 的结论组装成一份精炼 PRD：
- 一句话定位 + 目标用户 + 核心用例 + 差异化
- MVP 功能清单 + 不做清单
- 成功指标 + 致命假设 + go/no-go 阈值
- 标注所有 `[assumption]`（待验证项清单）

产出后询问用户：是否在开发前跑一遍**可选精益 PMF 检查**（商业模式画布 / 真实客户访谈 / PMF 信号阈值）——对应参考流程的 Lean Canvas 三连（09-11，可选）。

## AI 工具站立项提示（贴合常见场景）

用户多数新项目是 AI 工具站/垂直工具，立项阶段额外审这几条：
- **单点功能还是高频工作流？** 单点小工具（一次一张图）转化天花板低；如果能服务一个**重复发生的工作流**（批量处理、多步骤产出），立项价值更高——立项时就要判断「这需求是一次性低频，还是天天要用的」
- **付费意愿意愿是否成立？** 立项就预估：能付费的人是谁、为什么愿意为「把这事儿做快/做对」掏钱？低频一次性工具很难收订阅费，要么走高客单一次性、要么就得往高频方向扩
- **技术可行性成本**：AI 能力用现成 API（LLM/视觉/合成）够吗？还是要自己训/调？现成 API 能立的最小版本，通常 1-2 天就能跑通验证
- **合规红线**（用户铁律）：改发票/账单、证书/证件、合同、银行/转账、聊天记录、身份证/护照、任何官方/法律/财务凭证——一律不碰，即使有搜索量。立项若撞上，Step 1 就提示并让用户换方向

## 恢复机制

- 每次完成一步，更新 `00-status.md`（哪步完成、产出文件、下一步）
- 用户中断/换窗口后，先读 `00-status.md` 从中断处继续，**不依赖聊天记忆**
- 用户已有外部调研成果？直接放进对应步骤 md，跳过该步问答

## 注意事项

- **用户是决策者**：每步 AI 只起草，用户批准后才算完成；用户说改就改
- **诚实标注**：网络搜索不到的 → `[assumption]`；访谈/评论证据 → 注明来源。禁止把猜测写得像事实
- **一次只问 1-2 个问题**：提问是引导不是拷问，回答简短也没关系，流程本身才重要
- **产出不是代码**：本 skill 只做业务立项思考，把 `08-prd.md` 交给后续 skill（MVP 构造/建站落地）使用
- **红线检查**：结合用户实战经验，若想法涉及合规风险（伪造凭证/证件/财务类工具等），Step 1 就要提示风险并让用户确认方向，不写进后续流程
- 与 `git-worktree-isolation` 配合：立多个项目时，每个项目在独立 worktree/分支开发
