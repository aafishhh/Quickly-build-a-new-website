# 构造 MVP：核心功能链路（动作链 + 页面承载功能）

## Overview

立项（`new-website-ideation`）回答「**为什么做**」，`mvp-scoping` 回答「**MVP 有哪些页面类型**」，本 skill 回答「**核心功能怎么做、用户怎么走完整条链路**」——把核心用例翻译成**可执行的功能流程**：

- **核心动作链**：用户从进来到完成任务的关键动作序列（端到端主链路）
- **每页承载的功能**：每个页面类型承载哪些核心功能动作
- **功能 ↔ 页面映射**：每个核心功能落哪个页面、做完这步下一步去哪

这是**页面类型（mvp-scoping）和单页块区（页面块区家族）之间的桥梁**：它给后续块区 skill 提供「每页要承载什么功能」的依据，让单页块区有的放矢。

## 分层定位（职责边界）

| Skill | 回答的问题 | 产出 |
|---|---|---|
| `new-website-ideation` | 为什么做（用户/痛点/最小做啥） | `08-prd.md` 业务结论 |
| `mvp-scoping` | MVP 有哪些页、每页干嘛、怎么连 | 页面清单与信息架构 |
| **`mvp-function-flow`（本）** | **核心功能怎么做、动作链怎么走** | **功能链路（动作链 + 每页承载功能）** |
| 页面块区 skill | 每个页面内部块区结构 + UI | 逐页的块区/UI 规范 |
| `tool-site-foundation` | 用什么技术做（暂缓） | 基建方案 |

**边界（重要）**：本 skill **不拆到 UI/按钮/组件层面**，也不定单页块区。它只定「**有哪些核心功能动作、它们按什么顺序串成链路、各落哪个页面**」。「一个按钮长什么样」是页面块区 skill 的事。

## 分工铁律：mvp-scoping vs 本 skill

- **mvp-scoping 定「有哪些页面类型」**：首页 / 工具页 / 结果页 / 工作台 / about……（**页面层面**）
- **本 skill 定「核心功能怎么做」**：用户要完成的核心动作，拆成几步动作链、每步落哪个页面（**功能层面**）
- 顺序颠倒会踩坑：先有页面清单（mvp-scoping），再细化功能链路（本 skill）——页面类型是功能链路的载体
- 若某功能动作落不了现有页面、或某页面承载不了任何核心功能→回 `mvp-scoping` 增删页面，两边对齐

## Step 1: 锁定核心用例与输入

- 读 `mvp-scoping` 的 `22-mvp-summary.md`（页面清单）+ `new-website-ideation` 的 `08-prd.md`（MVP 范围、不做清单、核心用例）
- 明确：**产品最核心的 1 个动作**是什么（用户来这网站要完成的本质动作）
- 列出该动作的**关键输入/前置**（用户需要先提供什么、先满足什么才能开始）

## Step 2: 画核心动作链（端到端主链路）

把核心用例拆成**用户视角的动作序列**，从进来到完成（+ 必要时到管理/复用）：

```
进入（首页/入口） → 准备（登录?选参数?） → 完成核心动作 → 看结果 → （管理/复用/导出?）
```

- **每步一个动作动词**：进 → 选 → 输 → 处理 → 看 → 存/下载
- **尽量闭环、不跳页**：链路上每步的「下一步去哪」要明确，用户不停顿在死胡同
- **标 MVP 主链路 vs 可选支线**：主线是最短完成路径；支线（二次操作）MVP 阶段可砍
- **用 mermaid/文本层次画图**：节点 = 功能动作（不是页面），边 = 「做完这步下一步」

## Step 3: 每页承载的核心功能动作

对照 `mvp-scoping` 的页面清单，**每个页面类型列出它承载的核心功能动作**：

```
<页面类型>：承载动作 = [动作1, 动作2, …]（职责一句话）
```

- 一页一主责：每个页面尽量 1 个主功能动作 + 少量辅助（避免页面职责臃肿）
- 不承载核心功能的页面：`About/Privacy/Terms` 等基础页天然无核心功能，标「内容页，无核心动作」即可
- 工作台/结果页等管理类：列出承载的「查看/管理/复用」动作

## Step 4: 功能 ↔ 页面映射 + 衔接

产出映射表：**每个核心功能动作 → 落哪个页面 → 做完下一步去哪**：

| 功能动作 | 落哪个页面 | 做完下一步 |
|---|---|---|
| 选择/输入参数 | 工具页 | → 触发处理 |
| 处理/生成 | 工具页（或后台） | → 看结果 |
| 查看结果 | 结果页 | → 下载 / 回工具页改参数 |
| 管理历史 | 工作台 | → 复用 / 导出 |

- **衔接 = 功能衔接而非导航链接**：做完这步的产物 → 驱动下一步（如「输入完成」→「触发处理」→「结果页展示产物」）
- 检查**闭环**：链路无断点；每页的「出」能接上另一页的「进」
- 标注哪些衔接 MVP 可简化（如登录墙可后置）

## Step 5: 汇总功能链路（30-function-flow.md）

组装成给后续块区 skill 的依据：
- 核心动作链（端到端主链路 + 可选支线）
- 每页承载的核心功能动作清单
- 功能↔页面映射 + 衔接
- 所有 `[assumption]`（未确认的功能 / 可后置的衔接）
- **明确标注**：本清单不含 UI/按钮/单页块区，那部分由页面块区 skill 承接

产出后即可进入：对每个含核心功能的页面类型调用**页面块区 skill**（此时已知「这页要承载什么功能」，块区设计有依据）。

## 恢复机制

- 每完成一步更新 `00-status.md`（承接立项/mvp 的 00），标到哪、下一步
- 中断/换窗口后先读 `00-status.md` 接续
- 功能链路与页面清单冲突（某功能落不了页/某页空载）→ 回 `mvp-scoping` 对齐页面，不硬塞

## 注意事项

- **用户是决策者**：AI 起草功能链路，用户批准核心动作链后才算完成
- **只到功能层面**：不拆 UI/按钮/组件；不写单页块区（那是页面块区 skill 的职责）
- **主链路最短闭环**：优先保证「进→完成→看结果」能走通，支线/优化项 MVP 砍掉
- **功能落不了页就回 mvp-scoping**：不硬塞进现有页面，增删页面两边对齐
- **诚实标注**：功能必需性/可后置衔接不确定 → `[assumption]`
- **合规红线**：涉及伪造凭证/证件/财务类功能（立项已拦）一律不列
- 与 `git-worktree-isolation` 配合：文档随项目走，独立 worktree/分支
